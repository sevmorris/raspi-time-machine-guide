1.

Overview

at a glance

This guide covers building, operating and troubleshooting a macOS Time Machine destination on a Raspberry Pi, served over SMB. The configuration is vendor-neutral and uses only Debian / Raspberry Pi OS packages.

Every command uses generic placeholders. Substitute your own values before you run anything:

1.2

Pre-flight Checklist

before you start

Confirm all of the following before you begin.

  • The Raspberry Pi runs Debian 12 (bookworm) or later.
  • The Pi is connected by Ethernet. Wi-Fi works, but it is slower and less reliable for backups.
  • The USB SSD is connected and appears in lsblk.
  • The USB SSD is large enough. Typical guidance is 1.5–2× the size of the Mac's storage.
  • The Mac runs macOS 10.15 (Catalina) or later. Time Machine over SMB is well supported from Catalina onward.
  • You know which username will own the share.
Why Ethernet Matters
Backup throughput over Wi-Fi is typically 3–5× slower, and mid-backup disconnects are far more common. The first backup copies everything, so this is the difference between hours and days.

System Architecture

what talks to what
Table 1.3-1. Components
LayerComponentRole
HardwareRaspberry Pi 4 + USB SSDHost and backup storage
Filesystemext4 at /mnt/timemachineHolds the sparsebundle
Sharesmbd (Samba)Serves the share over SMB, port 445
Discoveryavahi-daemonAdvertises the share over Bonjour / mDNS

macOS writes a .sparsebundle to the SMB share. Samba's fruit VFS module supplies the Apple-specific behaviour that makes the share acceptable to Time Machine.

2.

Quickstart Runbook

ten steps, start to finish

These ten steps take a clean Raspberry Pi to a working Time Machine destination. Each step is safe to repeat. Sections 3 and 4 give the full detail behind them.

Step 1

Update and install the packages

sudo apt update && sudo apt -y install samba avahi-daemon
Step 2

Prepare the USB SSD

Identify the device, format it if necessary, and read its UUID.

lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINT    # identify the drive (e.g. /dev/sda1)
sudo mkfs.ext4 /dev/sda1                # format as ext4
sudo blkid /dev/sda1                    # copy the UUID for fstab
Warning — mkfs Destroys Data
The mkfs.ext4 command erases the target device. Confirm the device name in lsblk first, and skip this step if the disk is already formatted.
Step 3

Create the mount point and set permissions

sudo mkdir -p /mnt/timemachine
sudo chown <username>:<username> /mnt/timemachine
sudo chmod 755 /mnt/timemachine
Step 4

Mount the SSD

Add the UUID line to /etc/fstab (Section 3.1), then mount and verify.

sudo mount -a
mount | grep /mnt/timemachine            # verify it is mounted
Step 5

Create the Samba user

sudo smbpasswd -a <username>             # prompts for the SMB password

If <username> does not yet exist as a Linux user, run sudo adduser <username> first.

Step 6

Configure Samba

Apply the smb.conf from Section 3.2, then test and restart.

testparm -s
sudo systemctl restart smbd
Step 7

Enable the services at boot

sudo systemctl enable smbd avahi-daemon
Step 8

Advertise over Bonjour

Samba's mdns name = mdns is sufficient for most setups. To use a custom Avahi service file, see Section 3.3, then restart Avahi.

sudo systemctl restart avahi-daemon
Step 9

Connect from macOS

In Finder, choose Go → Connect to Server and enter the share address. Then add it in System Settings → Time Machine.

smb://<pi-hostname>/<share-name>
Step 10

Verify from macOS

tmutil destinationinfo
smbutil statshares -a
3.1

/etc/fstab

persistent mount

Mount the backup disk by UUID, never by device name: /dev/sda1 can change between boots.

proc            /proc           proc    defaults          0       0
PARTUUID=<boot-partuuid>  /boot/firmware  vfat    defaults          0       2
PARTUUID=<root-partuuid>  /               ext4    defaults,noatime,lazytime  0       1
# a swapfile is not a swap partition, no line here
#   use  dphys-swapfile swap[on|off]  for that
UUID=<your-disk-uuid>  /mnt/timemachine  ext4  defaults,noatime,lazytime,nofail,x-systemd.device-timeout=10  0  2
Caution — Substitute Your Own UUID
Read your disk's UUID with sudo blkid /dev/sda1 and replace <your-disk-uuid>. The nofail option matters: without it, the Pi refuses to finish booting when the USB disk is absent.
3.2

/etc/samba/smb.conf

the whole configuration

The fruit VFS module supplies the Apple-specific behaviour. The [TimeMachine] share section is what makes macOS accept the target.

[global]
   server role = standalone server
   workgroup = WORKGROUP

   # Protocols
   server min protocol = SMB2
   client min protocol = SMB2
   client max protocol = SMB3

   # Discovery (NetBIOS off; Avahi/mDNS handles TM)
   disable netbios = Yes
   mdns name = mdns

   # Security / integrity
   server signing = if_required   # "auto" is a valid alias; testparm normalizes it to this
   # smb encrypt = required       # optional, CPU cost; recommended on untrusted networks

   security = user
   map to guest = never

   # macOS compatibility
   vfs objects = catia fruit streams_xattr
   fruit:encoding = native
   fruit:resource = stream
   fruit:metadata = stream
   fruit:locking = none
   fruit:zero_file_id = yes

   # Bind to loopback + local subnet only (adjust /24 if your subnet mask differs)
   interfaces = lo <LAN_IP>/24
   bind interfaces only = yes

   # (Optional) Drop legacy port 139; use modern 445 only
   smb ports = 445

   # Misc
   idmap config * : backend = tdb
   load printers = no
   printing = bsd
   printcap name = /dev/null

   ntlm auth = ntlmv1-permitted   # use ntlmv2-only if all clients support it

[TimeMachine]
   path = /mnt/timemachine
   read only = No
   valid users = <username>
   create mask = 0600
   directory mask = 0700
   veto files = /._*/.DS_Store/
   vfs objects = fruit streams_xattr
   fruit:time machine = yes
   fruit:time machine max size = 800G
Note — The Two Lines That Matter Most
fruit:time machine = yes is what advertises the share as a Time Machine target. fruit:time machine max size caps how much space Time Machine believes it has, which is how you stop backups consuming the whole disk.
3.3

Avahi Service File

optional, for explicit discovery

Samba's mdns name = mdns handles basic advertisement. A custom Avahi service file makes Time Machine discovery more explicit, which helps on networks where mDNS is unreliable.

<?xml version="1.0" standalone='no'?>
<!DOCTYPE service-group SYSTEM "avahi-service.dtd">
<service-group>
  <name replace-wildcards="yes">%h</name>

  <service>
    <type>_smb._tcp</type>
    <port>445</port>
  </service>

  <service>
    <type>_device-info._tcp</type>
    <port>9</port>
    <txt-record>model=TimeCapsule8,119</txt-record>
  </service>

  <service>
    <type>_adisk._tcp</type>
    <port>9</port>
    <txt-record>dk0=adVN=TimeMachine,adVF=0x82</txt-record>
    <txt-record>sys=adVF=0x100</txt-record>
  </service>
</service-group>

Save it as /etc/avahi/services/timemachine.service, then restart Avahi.

sudo systemctl restart avahi-daemon
Note — A Log Message You Can Ignore
No service file found in /etc/avahi/services is normal. Samba's built-in mDNS is sufficient for most setups.

5.2

Backup and Recovery

protect the configuration

Back up the Pi configuration

Three files reconstruct the whole setup:

/etc/samba/smb.conf
/etc/fstab
/etc/avahi/services/timemachine.service   # if you created one

Capture them together:

sudo tar czf ~/pi-timemachine-config-$(date +%F).tar.gz \
  /etc/samba/smb.conf /etc/fstab /etc/avahi/services/

Recover the data if SMB fails

The sparsebundle sits on a plain ext4 filesystem, so it stays reachable even when smbd will not start. Mount the SSD on any Linux machine and copy the .sparsebundle directory off with rsync. On macOS you can then open it directly in Finder or Disk Utility.

Migrate to a new Pi or a larger disk

  1. Copy the sparsebundle off the old disk: rsync -avP /mnt/timemachine/ /mnt/new-disk/
  2. Update the UUID in /etc/fstab to the new disk's UUID, from sudo blkid
  3. Restore smb.conf, then sudo systemctl restart smbd
  4. On macOS, remove and re-add the destination. Time Machine recognises the existing sparsebundle.
Tip — The Sparsebundle Is the Backup
Everything else in this guide is reproducible in an afternoon. The sparsebundle is not. If you copy one thing off a failing Pi, copy that.
5.3

Performance Tips

when backups drag
  • Use Ethernet, not Wi-Fi. Throughput over Wi-Fi is typically 3–5× slower and far more prone to mid-backup disconnects.
  • Use a USB 3.0 SSD rather than a USB 2.0 spinning disk. Write speed dominates the first backup, which can move hundreds of gigabytes.
  • Check I/O wait when backups feel sluggish. High %util on sda means the SSD is the bottleneck.
iostat -x 2    # requires sysstat: sudo apt install sysstat
  • Suspect USB power if the drive disappears from lsblk. This is a common cause of dropouts on the Pi 4. A powered USB hub, or a Pi 5 with better USB power delivery, resolves it.
  • log2ram keeps logs in RAM to reduce SD card wear. It is visible in df -hT output and is already active on this setup.
5.4

Sizing and Quotas

how much to allocate

Set fruit:time machine max size to 70–90% of the dedicated disk. The reference configuration uses 800G on a 1 TB disk, which leaves sensible headroom.

Without a quota, Time Machine assumes the entire filesystem is available and will grow until the disk is full.

6.

Troubleshooting Playbook

symptom first

Each heading is a symptom. Work down the list under the one that matches.

The share does not appear in Time Machine settings

  1. Confirm Avahi is running: systemctl status avahi-daemon
  2. Confirm fruit:time machine = yes is set in the [TimeMachine] share section.
  3. Connect manually first in Finder (smb://<pi-hostname>/TimeMachine), then check System Settings → Time Machine.
  4. If mDNS discovery is unreliable on your network, connect by address instead: smb://<LAN_IP>/TimeMachine

macOS repeatedly asks for a password

  • Remove stale Keychain entries. Open Keychain Access, search for the Pi hostname, delete every matching item, then reconnect.
  • Verify the SMB user exists: sudo pdbedit -L should list <username>.
  • Confirm valid users = <username> in smb.conf matches the account name exactly.

NT_STATUS_NTLM_BLOCKED

Use SMB2/3 only, and permit modern NTLM where the client needs it.

server min protocol = SMB2
client min protocol = SMB2
ntlm auth = ntlmv1-permitted

Then remove the stale Keychain items for the server on macOS and reconnect.

The share is visible but will not mount

  • Verify ownership of the mount point: ls -la /mnt/timemachine should show <username>.
  • Confirm the SSD is actually mounted: mount | grep /mnt/timemachine
  • Check journalctl -u smbd for ACL or path denials.

Backups stall or fail mid-backup

  • Check network stability. A wired connection is strongly preferred.
  • Check USB errors: dmesg | grep -i usb for power or reset messages. A powered hub helps on the Pi 4.
  • Check disk health: sudo smartctl -a /dev/sda, which needs smartmontools.
  • If the sparsebundle is corrupted, repair it from macOS:
hdiutil repair /Volumes/TimeMachine/<ComputerName>.sparsebundle

Or open Disk Utility, select the sparsebundle, and run First Aid.

Backups are very slow

  • Confirm you are on Ethernet, not Wi-Fi.
  • Check disk I/O with iostat -x 2. High %util on sda points at the SSD.
  • The first backup is always slow because it copies everything. Later backups are incremental and much faster.

fruit_get_bandsize / fruit_tmsize_do_dirent warnings

You may see log messages like these:

fruit_get_bandsize: Didn't find band-size key in [...sparsebundle/Info.plist]
fruit_tmsize_do_dirent: Processing sparsebundle [...] failed
Note — These Warnings Are Harmless
The fruit module reads the sparsebundle's band size to estimate quota usage. When the band-size key is missing from Info.plist — common with bundles macOS created — Samba falls back to default behaviour. Backups still work correctly. Only Samba's internal size estimate is affected.
